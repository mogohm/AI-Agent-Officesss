# VISUAL-2026-001-ASSET-RECOVERY-001 — Canonical Asset Recovery

| Field | Value |
|---|---|
| Decision ID | `VISUAL-2026-001-ASSET-RECOVERY-001` |
| Mission | VISUAL-2026-001 |
| Status | **ACCEPTED** |
| Supersedes | nothing — v1.0.0 remains historically intact |
| Repository state | `b234810` |

## Context

The approved v1.0.0 canonical source bytes are unrecoverable. They existed only
inside a gitignored mission worktree on an environment that is no longer
reachable (see `artifacts/WP-002R/blocker-canonical-source.md`).

Production cannot consume assets that no longer exist. WP-002P has no source to
promote, so every downstream visual package is permanently gated.

## Decision

Create a **new canonical baseline v1.1.0** by reconstruction, and do **not**
overwrite v1.0.0.

| Baseline | Meaning |
|---|---|
| **v1.0.0** | Historically approved. Attestation valid at time of review. Source bytes `SOURCE_BYTES_UNRECOVERABLE`. Retained unmodified as mission history. |
| **v1.1.0** | Reconstructed recovery baseline. Becomes the production baseline for continued delivery. Parent: v1.0.0. |

The v1.0.0 digest `2c7a7093…ce76` is **retired, not reused**. v1.1.0 receives a
freshly computed digest over its own bytes, using the identical deterministic
algorithm (sorted `assetKey:sha256`, newline-joined, UTF-8 SHA-256).

## Rationale

Three alternatives were considered:

1. **Substitute legacy assets** — rejected. The legacy `*-floor-band/base.webp`
   art predates WP-002 (commit `dfb27ef`) and was rejected by WP-001 for
   `suspectedBakedCharacters`. It does not satisfy the empty-floor requirement.
2. **Overwrite v1.0.0 with regenerated bytes** — rejected. That would make the
   existing WP-002/WP-002H attestations retroactively false, destroying audit
   truth to preserve a version number.
3. **Re-cut as v1.1.0** — accepted. Production gets working assets; history stays
   honest; the digest change is explicit and traceable to this decision.

## Consequences

- `OFFICE_ASSET_BASELINE.version` → `1.1.0` and `.digest` → new value, but **only
  after** WP-002R, the v1.1.0 attestation, and WP-002P-R have all passed.
- Registry **paths do not change**. The 17 public URLs are already correct;
  only the pinned metadata moves.
- WP-002 and WP-002H remain PASSED against v1.0.0 and are not re-opened.
- The root cause is addressed by a durability requirement (§14): approved v1.1.0
  bytes must exist in **two** durable locations before WP-002R can pass, so this
  loss cannot recur.

## Consequence for regeneration cost

Reconstruction invokes an image provider for up to 17 assets with a bounded
retry budget (max 5 candidates each). This is real spend and requires the owner
to supply provider access; it is not incurred until credentials exist.
